## 三、API 矩阵 — 12 个 Controller，50+ 个端点

### 3.1 ChatController — 对话服务 (`/api/chat`)

| 方法 | 端点 | 功能 |
|------|------|------|
| POST | `/api/chat` | 同步对话，Graph 引擎全链路执行 |
| POST | `/api/chat/stream` | SSE 流式对话（RAG 检索 → 推理 → 回答分步推送） |
| POST | `/api/chat/stream-graph` | SSE Graph 节点级流式输出（每个节点完成时实时推送） |
| POST | `/api/chat/clear` | 清空会话历史 |
| GET | `/api/chat/history` | 查询会话历史消息 |
| GET | `/api/chat/sessions` | 查询用户会话列表（最多 50 条） |

**对话流程**：
1. 接收 `sessionId` + `question` + `userId`
2. Graph 引擎执行 `compiledGraph.invoke(initialState)`
3. 结果从 `final_response` 提取
4. 消息持久化到 MySQL（chat_session + chat_message）
5. 内存中保留最近 40 条历史

### 3.2 AlarmController — 告警诊断服务 (`/api/alarm`)

| 方法 | 端点 | 功能 |
|------|------|------|
| POST | `/api/alarm/receive` | 接收告警事件，写入 alarm_task 表 |
| POST | `/api/alarm/diagnose` | SSE 流式告警诊断（设备档案预取 + alarm_diagnosis_graph 执行） |
| GET | `/api/alarm/diagnose/{taskId}/status` | 查询诊断任务状态和结果 |
| POST | `/api/alarm/resume/{taskId}` | 从检查点恢复中断的诊断任务 |
| GET | `/api/alarm/checkpoint/{taskId}` | 查询任务全部检查点记录 |

**告警字段**：alarmId, station, deviceId, deviceName, deviceType, alarmType, alarmLevel, alarmSource, currentValue, threshold, duration

**诊断流程**：
1. 从 alarm_task 表加载告警上下文
2. 预取设备档案和设备状态（MockDataLoader）
3. 构建诊断输入（含设备上下文 JSON）
4. 通过 `alarm_diagnosis_graph` 流式执行
5. 完成后更新 alarm_task 状态和诊断结果
6. 支持断点恢复

## 四、Graph 执行引擎 — 21 个节点，2 条主链路

### 4.1 主链路 `power_ops_workflow`

```
START → pre_check → context_load → router
  ├─ [knowledge_qa] → query_rewrite → rag_retrieve → tool_execute
  │                     → rerank → react_qa_agent → answer_review
  │                       ├─ [retry] → rag_retrieve
  │                       └─ [pass] → citation_check → safety_review
  ├─ [diagnosis] → entity_extract → alarm_rag_retrieve → planner
  │                  → executor → evidence_validation
  │                    ├─ [ok] → diagnosis → risk_assessment → replanner
  │                    │         ├─ [retry] → executor
  │                    │         └─ [done] → action_recommend
  │                    └─ [incomplete] → replanner / action_recommend
  └─ [chat] → chat → safety_review

→ final_response → memory_save → END
```

**路由逻辑 (IntentDispatcher)**：
- `knowledge_qa`：知识问答 → 进入 RAG 检索链路
- `diagnosis`：诊断分析 → 进入诊断链路
- `chat`：自由对话 → 进入聊天链路

**条件分支**：
- `AnswerReviewDispatcher`：答案不满意 → 重新检索；满意 → 引用检查
- `EvidenceValidationDispatcher`：证据充分 → 直接诊断；不足 → 重规划/处置建议
- `ReplannerDispatcher`：需要重试 → 回到 executor；完成 → 处置建议

### 4.2 告警诊断专线 `alarm_diagnosis_graph`

```
START → pre_check → context_load → entity_extract → alarm_rag_retrieve
→ planner → executor → evidence_validation
  ├─ [ok] → diagnosis → risk_assessment → replanner
  │           └─ [retry] → executor
  └─ [skip] → action_recommend
→ safety_review → final_response → memory_save → END
```

**与主链路的区别**：告警专线跳过了 router 节点，直接进入诊断链路，且无 chat/knowledge_qa 分支。

### 4.3 全部 Graph 节点详情

| 节点名 | 实现类 | 所属子图 | 功能描述 |
|--------|--------|----------|----------|
| `pre_check` | PreCheckNode | - | 输入验证（空值检查、长度限制、敏感词过滤） |
| `context_load` | ContextLoadNode | - | 加载历史记忆、加载知识组织 Workflow 上下文、执行 PreGraph 钩子 |
| `router` | RouterNode + IntentDispatcher | - | 意图识别，返回 knowledge_qa / diagnosis / chat |
| `query_rewrite` | QueryRewriteNode | knowledge | 查询改写 + RBAC 权限校验 |
| `rag_retrieve` | RagRetrieveNode | knowledge | 混合检索（Milvus 向量 + MySQL 关键词 + 知识图谱） |
| `tool_execute` | ToolExecuteNode | knowledge | AI Agent 工具调用 |
| `rerank` | RerankNode | knowledge | 检索结果重排序 |
| `react_qa_agent` | ReactQaAgentNode | knowledge | ReAct 模式问答 Agent（Think → Act → Observe 循环） |
| `answer_review` | AnswerReviewNode | knowledge | 答案质量审核（支持 retry 循环回 rag_retrieve） |
| `citation_check` | CitationCheckNode | knowledge | 引用溯源检查 |
| `entity_extract` | EntityExtractNode | diagnosis | 实体抽取（设备 ID、温度值、参数等） |
| `alarm_rag_retrieve` | RagRetrieveNode | diagnosis | 告警相关上下文 RAG 检索 |
| `planner` | PlannerNode | diagnosis | 诊断排查计划生成 |
| `executor` | ExecutorNode | diagnosis | 工具调用执行 + Resilience4j 重试 + 结果验证 |
| `evidence_validation` | EvidenceValidationNode | diagnosis | 证据质量评估，条件分发到 diagnosis / replanner / action_recommend |
| `diagnosis` | DiagnosisNode | diagnosis | 诊断结论生成 |
| `risk_assessment` | RiskAssessmentNode | diagnosis | 风险评估 |
| `replanner` | ReplannerNode | diagnosis | 重规划（可循环回 executor 重新取证） |
| `action_recommend` | ActionRecommendNode | diagnosis | 处置建议生成 |
| `chat` | ChatAgentNode | chat | 自由对话 |
| `safety_review` | SafetyReviewNode | - | 安全审核（检查输出合规性） |
| `final_response` | FinalResponseNode | - | 最终响应格式化 |
| `memory_save` | MemorySaveNode | - | 记忆持久化 |

## 八、知识组织层 (Knowledge Organization)

### 8.1 核心服务

**KnowledgeOrganizationService** 是整个系统的"大脑"，负责：
- 加载工作流模板 + 知识图谱节点/边
- BGE-M3 语义匹配 + 关键字词法匹配
- 执行计划生成 + 就绪检查
- 工具别名映射

### 8.2 数据模型

| 模型 | 来源文件 | 功能 |
|------|----------|------|
| WorkflowTemplate | `workflow_templates.json` | 工作流模板（场景/dispatch步骤/tool/slots） |
| KnowledgeGraphNode | `nodes.json` | 知识图谱节点（设备/工具/规程/案例等实体） |
| KnowledgeGraphEdge | `edges.json` | 知识图谱边（父子/依赖/引用等关系） |
| KnowledgeOrgMatch | 运行时计算 | 匹配结果（命中模板+候选节点+推荐工具+执行步骤+执行预检） |
| WorkflowStep | 模板内嵌 | 模板步骤定义（step/tool/params/slots） |
| schema.json | `schema.json` | 知识图谱 Schema |

### 8.3 语义匹配引擎

**双路打分机制**：
1. **BGE-M3 语义相似度**：将查询和模板/节点分别向量化，计算余弦相似度
2. **关键字词法匹配**：精确匹配 + Token 分词匹配，加权评分
3. **综合评分**：`totalScore = semantic × 8.0 + lexical_normalized × 4.0`

**智能推断**：
- 设备类型推断：文本包含"主变/变压器"→主变压器，"母线"→母线，"线路"→线路，"负荷/转供"→负荷/馈线
- 风险等级推断：文本含"N-1/全停/风险"→HIGH，"校核/操作"→MEDIUM，其余→LOW
- 工具别名映射：`regulation_retriever → searchSafetyRules`、`source_scanner → queryInternalDocs`、`graph_query → queryKnowledgeGraph` 等 21 个映射
- 执行图谱推断：含"告警/油温/阈值/alarm"→alarm_diagnosis_graph，其余→power_ops_workflow

### 8.4 知识图谱查询

- 按分类和关键词过滤节点
- BFS 遍历相关节点（支持深度参数）
- 查看关联边

## 九、RAG 检索引擎

### 9.1 架构

```
用户查询 → HybridSearchService → Milvus 向量检索 (BGE-M3)
                                → MySQL 关键词检索
                                → 知识图谱搜索
         → RerankService → 重排序 → 上下文注入 → LLM 生成
```

### 9.2 核心组件

| 类 | 功能 |

## 二十五、整体功能总结

GridOpsAgent v9 是一个**面向电网调度与运维场景的多智能体诊断原型系统**，基于 Spring Boot + Spring AI Alibaba Graph 构建，实现了完整的三层资产架构：

```
Workflow（工作流）→ Skill（技能）→ Agent（智能体）
    │                    │                │
  处置顺序             专业能力          运行时调用
```

**核心能力闭环**：
1. **知识入库**：文档上传 → 解析 → 分块 → BGE-M3 向量化 → Milvus 索引
2. **任务编排**：自然语言输入 → 知识组织语义匹配 → 命中 Workflow/Skill/Graph → 生成执行计划
3. **诊断执行**：Graph 引擎驱动 → 路由分发 → RAG 检索 → 工具调用 → 证据验证 → 诊断推理 → 风险评估 → 处置建议
4. **安全审核**：每个输出经过 Safety Hook + Human Approval Hook
5. **可观测**：全链路 Trace、节点检查点、工具调用日志
6. **结果持久化**：会话/消息/诊断任务全部写入 MySQL

**前端 7 个工作区覆盖了从编排到执行到运维的完整工作流。**
