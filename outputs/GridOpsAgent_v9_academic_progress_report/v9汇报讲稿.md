# GridOpsAgent v9 工作进展汇报讲稿

适用场景：课题组组会 / 导师阶段性进展汇报  
建议时长：8-12 分钟  
汇报定位：说明最近完成了一个面向电网告警诊断的多智能体原型系统，重点讲清楚“为什么做、做到了什么、系统如何运行、后续怎么深化”。

## 开场建议

各位老师好，我这次汇报的是最近完成的一个 GridOpsAgent 原型系统。这个系统主要面向电网调度运维中的告警诊断任务，目标不是只做一个问答页面，而是把一个告警输入之后的任务理解、流程编排、工具查询、知识检索、证据组织和诊断报告生成串成一个可展示、可解释、后续可扩展的流程。

我会按四部分讲：第一是建设背景和技术构成，第二是系统总体流程，第三是几个核心页面和多智能体机制，最后用主变油温异常案例说明当前效果和后续计划。

## 第 1 页：工作进展汇报

这一页主要做一个总起。

可以这样讲：

这次工作主要围绕电网调度运维场景中的告警诊断展开。我目前完成的是一个多智能体诊断原型系统，系统名称是 GridOpsAgent。它的核心目标是把告警诊断从简单的问答，推进到一个有任务编排、有工具调用、有知识检索、有过程记录的诊断流程。

这里的“工作进展”主要包括三块：一是后端多 Agent Graph 流程的搭建，二是前端四个工作区的整合，三是知识库和知识拓扑能力的接入。

过渡：

下面先说明为什么要做这样一个过程化诊断系统。

## 第 2 页：研究背景与目标

这一页回答“为什么需要这个系统”。

可以这样讲：

电网告警诊断不是一个单点问题。一次告警往往需要同时查看设备状态、历史告警、运行日志、缺陷工单、规程条文和历史案例。传统问答式系统容易直接给结论，但中间缺少可检查的诊断过程，也不方便解释结论来自哪些信息。

所以我这次的目标是构建一个过程化诊断支撑系统。这里强调三点：第一，多源信息需要统一组织；第二，诊断任务本身包含识别、规划、查询、校核、复核和报告生成多个阶段；第三，当前阶段先完成一个可展示、可解释、可继续扩展的实验系统。

可以补一句：

也就是说，我希望系统不仅能回答“是什么原因”，还要能展示“系统查了什么、怎么查的、依据是什么”。

## 第 3 页：系统技术构成

这一页说明“系统用了哪些技术”。

可以这样讲：

从技术构成上看，系统分成四层。

第一层是前端展示层，主要是 HTML、CSS 和 JavaScript 实现的单页工作区，通过 SSE 接收后端流式事件，用来展示任务编排、诊断轨迹、知识拓扑和知识库运维。

第二层是后端服务层，主体是 Spring Boot。多智能体流程通过 Graph 方式组织，另外 MCP 工具服务和本地算子也被封装成可调用能力。

第三层是模型与知识层。DeepSeek 主要用于任务理解、规划和诊断报告生成；BGE-M3 用于本地文本向量化；RAG 和知识组织图谱用于补充规程、案例和结构化关系。

第四层是数据与中间件。MySQL 用于文档、日志和业务记录，Milvus 用于向量索引和语义检索，Redis 目前作为后续缓存和会话扩展预留。

过渡：

有了这些基础组件以后，系统整体流程可以抽象成下一页这条路线。

## 第 4 页：总体技术路线

这一页讲“从输入到报告是怎么走的”。

可以这样讲：

系统的总体路线是从告警输入开始，经过任务理解、流程编排、工具执行、证据复核，最后生成诊断报告。

用户输入一个自然语言告警，比如“主变 TR-110KV-001 油温 86℃ 超过 80℃阈值，请诊断”。系统首先识别里面的设备、异常类型和阈值信息，然后匹配相应的诊断流程模板，再生成排查步骤。

后续 Graph 会根据计划调用工具，包括设备状态、告警历史、日志、工单、规程和知识库检索。拿到这些证据后，再由后面的节点做证据复核、安全检查和最终报告组织。

这里我想强调的是：这个流程不是一次性让模型自由回答，而是把诊断任务拆成了多个可观察、可记录的步骤。

## 第 5 页：阶段性完成内容

这一页概括“目前完成了哪些模块”。

可以这样讲：

当前系统已经完成四类能力的集成。

第一是任务编排台，用来把自然语言任务映射到流程模板、候选步骤和关联知识节点。

第二是运行诊断控制台，用来执行真正的 Graph 诊断流程，并展示节点状态和工具返回。

第三是知识拓扑，用来组织流程模板、工具能力和知识实体之间的关系。

第四是知识库运维，支持文档上传、切片、向量化、健康状态监测和检索自检。

所以现在系统已经不是单独几个接口，而是形成了一个相对完整的交互和运行闭环。这里如果担心“闭环”说法太套，可以现场改成“完整流程”。

## 第 6 页：任务编排台

这一页讲第一个页面。

可以这样讲：

任务编排台的定位是执行前的任务理解和流程预组织。用户输入一个调度或运维任务后，系统会先解析任务中的设备对象、异常类型、阈值和诊断意图。

然后系统会根据内置的流程模板进行匹配，比如主变油温异常诊断、N-1 风险校核、负荷转供校核等。匹配完成后，页面会展示候选步骤、推荐工具和关联知识节点。

这一页的意义是，在真正执行诊断之前，先让用户看到系统准备按什么思路处理这个任务。这样后面的多 Agent 执行就不是一个黑箱过程。

## 第 7 页：运行诊断控制台

这一页讲真正执行诊断的地方。

可以这样讲：

运行诊断控制台是系统真正执行 Graph、多 Agent 和工具调用的页面。它会按顺序运行 Router、Planner、Tool、Evidence、Safety、Report 等节点。

这里我做了一个重点改造：不是把所有工具调用结果直接堆在页面上，而是把执行过程折叠成轨迹，让用户可以展开查看。这样既保留溯源信息，又不会影响最终诊断结果的阅读。

在执行过程中，系统会记录节点状态、工具返回、失败原因和中间证据。最终报告会组织成诊断结论、原因线索和处置建议。

可以补一句：

这一页对应的是“系统实际做了什么”，不是简单的模板预览。

## 第 8 页：多智能体协作机制

这一页是机制页，建议讲得稍微专业一点。

可以这样讲：

系统内部按照诊断任务阶段划分了多个 Agent 或节点角色，它们共享同一个 Graph State。

RouterAgent 负责识别任务类型，判断是知识问答、告警诊断还是普通对话。WorkflowContextAgent 负责匹配流程模板、知识节点和推荐能力。EntityAgent 抽取设备、告警、阈值和时间信息。PlannerAgent 根据上下文生成诊断计划和工具调用步骤。

后面 Tool 和 Knowledge Agent 负责调用工具、检索规程案例和知识库内容。Evidence、Safety 和 Report 节点则负责证据复核、安全约束检查和最终报告组织。

这里的关键点是：各个 Agent 不是各自独立聊天，而是围绕同一份状态不断补充信息。这样可以把任务理解、证据收集和报告生成连接起来。

## 第 9 页：知识拓扑

这一页讲知识组织。

可以这样讲：

知识拓扑页面主要用来组织流程模板、工具能力和知识实体。这里借鉴了 nari_demo 里流程模板和知识图谱的组织方式，但后端已经迁移成 Java resources 和 Spring Boot 接口。

当前图谱里包含不同类型节点，比如流程、工具、设备或知识实体。它的作用不是直接替代诊断，而是给任务编排和诊断解释提供结构化依据。

例如一个主变油温异常任务，可以关联到主变设备、冷却器状态、油温规程、历史缺陷和相关工具。这样系统在规划时可以优先参考这些关系。

可以强调：

这部分为后续扩充更多调度运维场景留下了结构。

## 第 10 页：知识库运维

这一页讲 RAG。

可以这样讲：

知识库运维页面主要解决规程、案例、说明文档等非结构化资料的接入问题。当前已经支持文档上传、切片、向量化和检索验证。

页面里还加入了 RAG 健康面板，可以看到 MySQL、Milvus、Embedding API、文档数和 chunk 数等状态。如果 Milvus 不可用，系统会提示当前使用内存向量库，重启后会丢失。

我还加了一键 RAG 自检接口，它会上传一段测试文本，等待处理，然后进行检索验证，最后返回一个简洁的诊断结果。这个主要用于确认“上传到查询”的链路是否可用。

可以补一句：

Embedding 目前使用本地 BGE-M3，不消耗 DeepSeek token。

## 第 11 页：主变油温异常诊断流程示例

这一页是案例页，建议讲得具体一点。

可以这样讲：

这里用一个主变油温异常任务作为示例。输入条件是 TR-110KV-001 油温 86℃，超过 80℃报警阈值。

系统在诊断过程中组织了几类信息：设备状态、负荷率、冷却器状态、历史缺陷和规程资料。从运行结果看，负荷率约 92%，冷却器 #2 启动失败，并且相关缺陷已经登记后持续未处理。

因此系统生成的诊断线索主要包括三点：第一，冷却能力不足；第二，高负荷加剧温升；第三，存在重复故障风险。处置建议则包括降低负荷、投入备用冷却器、现场检查 KM2 接触器等。

可以强调：

这个案例的重点不是证明系统已经接入真实生产数据，而是证明这个诊断流程能够把输入、工具结果、知识检索和最终报告组织起来。

如果老师问“数据是真的吗”：

可以回答：当前设备状态和工单数据主要是演示用 mock 数据，目的是验证流程和交互。后续如果接入 EMS、PMS、SCADA 和工单系统，工具层可以替换成真实接口。

后续工作我计划从四个方向继续推进。

## 可能被问到的问题

### 1. 这个系统和普通大模型问答有什么区别？

可以回答：

普通问答通常是用户输入后直接生成答案。这个系统把诊断拆成了任务理解、流程编排、工具查询、知识检索、证据复核和报告生成多个步骤，并且每一步都有状态记录和结果溯源。因此它更适合电网这种需要依据、过程和安全约束的场景。

### 2. 当前数据是真实的吗？

可以回答：

当前设备状态、告警、日志和工单主要是 mock 数据，用于验证诊断流程和展示方式。RAG 上传、切片、向量化、检索链路是真实可运行的。后续如果接入 EMS、SCADA、PMS 和工单系统，工具层可以替换为真实接口。

### 3. nari_demo 的内容迁移到了哪里？

可以回答：

我没有继续依赖原 Python demo 运行时，而是把流程模板、知识图谱节点、边和 schema 迁移到了 Spring Boot 主应用的 resources 中。后端通过 `/api/knowledge-org` 系列接口加载和查询，前端用于任务编排和知识拓扑展示，Graph 中也会把匹配到的 workflow context 提供给 Planner。

### 4. RAG 是否能完整跑通？

可以回答：

当前上传、切片、向量化、入库和检索验证链路已经可以跑通。向量库优先使用 Milvus，如果 Milvus 不可用会回退到内存向量库。Embedding 默认使用本地 BGE-M3 服务，避免把文档向量化也消耗到 DeepSeek token。

### 5. 为什么还保留 mock/estimate？

可以回答：

因为目前还没有接入真实调度生产系统。为了先验证流程和前后端交互，我把电力工具和高级算子做成了结构化 mock 或规则估算，并在页面和报告中标注边界。这样后续接真实接口时，可以在不改整体流程的情况下替换工具实现。

### 6. 下一步最重要的工作是什么？

可以回答：

最重要的是接入真实数据源和规范工具返回字段。只要设备状态、告警历史、运行日志、工单和规程案例数据稳定接入，后面的 Graph 编排、RAG 检索和报告生成就能继续复用和深化。
